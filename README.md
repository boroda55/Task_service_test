# Task Service

Асинхронный сервис для управления и фоновой обработки задач.
Реализован на FastAPI с использованием RabbitMQ для очереди сообщений и PostgreSQL для хранения данных.

## Стек технологий

- Python 3.11
- FastAPI, SQLAlchemy 2.0 (async), Alembic
- PostgreSQL 14, RabbitMQ, aio-pika
- Pytest, httpx (для интеграционных тестов)

## Запуск проекта

1. Скопируйте файл с переменными окружения:
   ```bash
   cp .env.example .env
   ```

2. Запустите сервисы через Docker Compose:
   ```bash
   docker-compose up --build
   ```

3. Документация API (Swagger) будет доступна по адресу:
   http://localhost:8000/docs

## Миграции базы данных
Миграции применяются автоматически при старте контейнеров. Для ручного управления схемой:
```bash
    # Применить все ожидающие миграции
    docker-compose exec api alembic upgrade head
    # Проверить текущую версию миграции
    docker-compose exec api alembic current
```

## Тестирование

Тесты используют in-memory SQLite для изоляции и быстродействия.
Это обеспечивает мгновенный feedback loop и не требует поднимать реальный PostgreSQL.
Если нужен запуск тестов строго на PostgreSQL, архитектура позволяет переключить конфигурацию на testcontainers.

```bash
# Запуск всех тестов
pytest -v

# Запуск с отчетом о покрытии
pytest --cov=app --cov-report=term-missing
```

## Архитектурные решения

- Единая архитектура доступа к данным: Использован строгий паттерн Service/Repository. Слой репозитория инкапсулирует все CRUD-операции. Важно: Фоновый воркер (worker.py) также использует TaskRepository для работы с БД, что обеспечивает консистентность кода и упрощает его тестирование.
- Параллельная обработка: Воркер настроен с prefetch_count=10, что позволяет обрабатывать несколько задач одновременно без блокировки.
- Отказоустойчивость и защита от отравленных сообщений (Poison Pill): Воркер использует requeue=False при обработке сообщений. При возникновении ошибки воркер перехватывает исключение, сохраняет статус FAILED и текст ошибки в БД, а затем подтверждает сообщение (ACK). Это предотвращает бесконечный цикл перепотребления битой задачи, который мог бы заблокировать очередь. Для временных сбоев реализованы повторные попытки через tenacity.
- Идемпотентность: Воркер проверяет статус задачи перед началом обработки, игнорируя дубликаты сообщений из очереди (Idempotency guard).
- Работа со временем: Во всем проекте используются timezone-aware объекты (datetime.now(timezone.utc)).
- Управление схемой БД и безопасность: Создание и изменение таблиц выполняется исключительно через Alembic миграции (папка alembic/versions/ закоммичена в репозиторий), create_all не используется. Конфигурация подключения читается из переменных окружения (.env), пароли не захардкожены в конфигурационных файлах (например, в alembic.ini).

## API Endpoints

| Метод | Путь | Описание |
|---|---|---|
| POST | `/api/v1/tasks` | Создание новой задачи |
| GET | `/api/v1/tasks` | Список задач (параметры: `status`, `priority`, `page`, `per_page`) |
| GET | `/api/v1/tasks/{task_id}` | Детальная информация о задаче |
| GET | `/api/v1/tasks/{task_id}/status` | Получение текущего статуса задачи |
| DELETE | `/api/v1/tasks/{task_id}` | Отмена задачи (перевод в статус CANCELLED) |
| GET | `/health` | Health check для мониторинга |
